# Agent Note: 聊天渠道的远程控制面板

Status: implemented

[English](2026-09-22-sidebar-channels-panel.md) | 中文

## Problem

Host 早已能由聊天平台驱动会话：`dsh-channel` 拥有连接器注册表，`dsh-channel-bridge` 拥有去重、聊天锁、准入与回复投递，`dsh-channel-tuitui` 适配本仓库唯一内置的传输，`dsh-api-channels` 在这一切之上发布 `channels` Remote 命名空间。但产品里够不到这些：用户看不到某个 Host 提供哪些渠道、某个渠道是否已连接、需要哪些凭据、由哪些字段配置；启用一个渠道意味着手工编辑设置文档并重启。

这次改动就是这条接缝的浏览器半边。

## Decision

该能力以一个全新的客户端插件包落地：`@deepseek-ai/dsh-client-ui-sidebar-channels`，把 `channels` 注册为右侧边栏的一种标签页类型：`builtin`、`available`、order 600，从引导页进入，指南条目序号 60。它是 `available` 而不是 `default-on`，理由与 terminal、git 页面相同：远程控制是用户主动要求的东西，常驻席位属于回答会话问题的界面。

**面板读取 Host 的描述符，不持有渠道配置的副本。** `channels.status` 报告每个渠道的连接、绑定的会话、最近一次失败、声明的能力以及凭据*引用*；渠道的设置描述符通过设置作用域的 `describe` 到达，`schema-form.ts` 把这份序列化 schema 变成正文要画的字段列表——每个字段的控件种类、某个 section 声明的可选值、字段回退到的 schema 默认值。因此新增连接器无需改动面板即可出现：在 Host 中注册它就够了，表单由它自己的 schema 决定。

**保存是一组操作，并带上读取时的 revision。** 表单把草稿暂存在标签页的 store 中；一次保存把它们变成设置操作，经已绑定的作用域 `mutate(ops, revision)` 提交，然后回读用户层判断写入是否落定。并发写入会被发现而不是被覆盖，而未生效的保存会保留草稿并如实说明，而不是凭乐观猜测清空表单。

**凭据只有引用名。** 卡片列出每个声明的凭据及其引用名、是否已配置、值来自哪里、是否可写。secret 角色的字段渲染为只写密码控件，面板从不回显，且仅在用户亲自输入时才写入。`enabled` 与 `sessionId` 属于桥接而不是连接器自身的配置，但渠道的 schema 声明了它们，面板渲染描述符持有的每个字段。

**面板不自造登录流程。** 需要扫码或交互式授权的平台在这里没有对应手势：Host 的 `AuthorizationPrompt` 没有声明 code 或二维码种类，因此用户看到的是连接器自己报告的失败行。

**渠道的描述符可能晚于设置镜像的那次答复，面板会修补这一点。** 桥在第一次 `channels.status`——也就是面板自己的第一次调用——时才绑定连接器、从而注册它的设置命名空间，因为桥先于连接器各行挂载，而注册表变化不会再触发一次绑定。注册一个解析值未发生变化的命名空间不会发出 `settings/document-updated`，客户端镜像又只在启动时读一次，所以它持有的答复可能既是最新的、又缺少面板刚刚得知的那个命名空间。当镜像没有为面板刚读到的渠道列表中的某个渠道提供命名空间时，面板通过 `remote.settings.describe()` 读一次设置文档，并把找到的结果经镜像自身的 `acceptView` 折回去，于是共享镜像仍是设置文档的唯一视图，表单在首次挂载时就出现，而不必等到重连。若某个部署的连接器配置与其 schema 默认值不同，注册时会发出该更新事件，此时修补发现没有缺失项，也就不会发起读取。

有三处偏离设计说明值得记录。设计说明假设客户端插件可以调用 `ctx.settings.register<Ns, T>()` 取得自己的命名空间；该调用是 Host 专用的，因此客户端通过 `ctx.settingsScope.describe()` 读取同一份描述符，并通过已绑定的作用域 `mutate` 写入。设计说明还假设 tsconfig 别名生成器会映射新包名；它只映射恰好等于 `@deepseek-ai/dsh-<目录名>` 的名字，因此客户端 UI 包需要在其他客户端 UI 别名旁手写一条别名。设计说明还把描述符读取当作一次普通的镜像读取；镜像的读取面没有暴露刷新入口，因此上述修补由面板自己完成。

## Alternatives considered

**为已知渠道手写表单字段。** 这会把推推的字段硬编码进面板，让每个未来的连接器都变成一次面板改动。描述符本来就携带 schema；按它渲染才使面板成为接缝，而不是一个推推专用界面。

**在客户端注册设置命名空间。** `ctx.settings.register` 是 Host 调用，拥有一个命名空间；客户端无法凭空造一个，假装可以就等于在连接器自己的注册旁再立一个权威。读取描述符并经作用域写入，花的正是已有的契约。

**在面板里做扫码或验证码登录。** `AuthorizationPrompt` 没有这类种类，面板只能自造一套 Host 并不提供的协议。失败行是诚实的；自造的流程不是。

**画出时间戳与聊天锁事实。** `lastErrorAt`、`lastInboundAt`、`lockedChatId`、`replyBudget` 会到达客户端，而卡片一个都不画：连接、绑定的会话、最近一次失败消息与声明的大小上限才是用户据此行动的东西，而卡片不是诊断表。

**启用渠道时不绑定到当前标签页的会话。** Host 的 `enable` 需要会话 id，而标签页本来就知道自己属于哪个会话。单独的会话选择器会让用户重复界面已经知道的事。

**隐藏面板无法编辑的字段。** 嵌套对象或未声明的控件种类会以它的 JSON 值出现，并附一行说明它不能在此编辑，因此面板只理解一部分的描述符，不会看起来像是完全理解的。

## Consequences

面板的完整程度取决于 Host 的描述符：一个不声明能力、不声明凭据、schema 为空的连接器，会渲染出一张只有连接状态的卡片和一个没有字段的表单，这是准确而不是故障。

这里没有任何内容被持久化。渠道是在挂载时与每次变更后读取的 Host 事实，草稿存在标签页的 store 里，刷新会重新读取一切；这也正是 store 留在这个包而不是客户端对象层的原因——这个面板是它唯一的消费者。

推推本身不提供任何界面，因此这个面板就是它的全部 UI：连接器注册自己，标签页按它注册的描述符把它渲染出来。

e2e 场景是 host 平面的程序：`apps/web/tests/sidebar-channels.e2e.ts` 启动发布组合，并与其他引入 scaffold 的 e2e 规格一样，同时登记在 `tsconfig.host.json` 与 `apps/web` 客户端工程的 `exclude` 中。它从不启用渠道——启用会打开到聊天平台的真实传输，而这个无密钥通道没有对应夹具——因此组装覆盖的是读取路径、描述符与凭据只显引用名的规则。
