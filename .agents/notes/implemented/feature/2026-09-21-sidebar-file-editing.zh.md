# Agent Note：从右侧栏编辑工作区文件

Status: implemented

[English](2026-09-21-sidebar-file-editing.md) | 中文

## Problem

右侧栏的文本 tab 只展示工作区文件，仅此而已。用户在阅读时发现一行有错，必须离开 harness、在磁盘上找到该文件、在那里改——而 harness 本身已经显示了确切的文本、确切的路径，以及解析它的那个 Session 工作区根。这个闭环的读的一半已经存在，写的一半没有。

加上它，会带出读的一半从不需要回答的问题：现在有两个写入者碰同一个文件。Agent 在用户打字时写这个文件，不能悄悄删掉 Agent 的工作；而用户输入的文字也不能被悄悄删掉。

## Decision

写入以已有文件命名空间上的一个方法进入（[`dsh-api-workspace-files`](../../../../packages/api/workspace-files/README.zh.md)），现成的查看器（[`dsh-client-ui-sidebar-textpreview`](../../../../packages/client/ui-sidebar-textpreview/README.zh.md)）长出编辑模式。没有新 tab 种类，没有新包。

**`workspaceFiles.write(path, content, expectedVersion)` 是唯一的变更操作。** 它替换文件的整段文本，并返回写入后文件的 `WorkspaceFileStat`，调用方无需再 `stat` 一次就知道新版本。`expectedVersion` 是调用方读到的那个 `version`——通常来自一页或一次 `stat`——它就是并发故事的全部：服务把它与新做的 `stat` 比较，不一致就以新增的 `workspace-file/stale-version` 代码拒绝，一致时把同一个值交给后端的原子替换，由它在写入内部再检查一次。因此调用方从不自己铸造版本，只回传别人给过它的版本；而服务替调用方伪造一个版本，恰恰会摧毁这道守卫存在的意义。Client 把这一种代码渲染为「文件已在磁盘上被修改，你的编辑没有保存」，并在旁边给出重新载入。

**保存不走 `fs/write-intent` 或 `fs/edit-intent`。** 那些瀑布及其喂给的「先读后改」策略由 Agent 自己的文件系统工具派发，而不是由 provider 或任何服务派发，而策略从这条路径并不具备的执行上下文中推导它的 owner。它对一个没有该文件观察记录的 actor 给出的书面答案是 `createIfAbsent`，而 provider 对已存在的文件会拒绝它——所以把人工保存接到瀑布上只会让每一次覆盖都不可能，而不是更安全。显式的 `expectedVersion` 参数正是为「非工具调用方」准备的缝，它强制执行的事实与策略从「在该版本上存在观察记录」推导出的事实相同，并且落在同一个原子区段内。保存由被寻址 Session 的沙箱策略围栏，服务随写入一并传入，所以不允许写自己工作区的 Session 也无法保存。

**写入之后什么都不发。** `fs/observed` 是 Agent Session 的读取记录；把人工保存记进去会让 Agent 覆盖一个它从未读过的文件，还会让保存者自己的变更提示条对着自己的写入弹出来。

**只为查看器完整持有的文件提供编辑。** 编辑器把整个文件写回，所以分多页读来的文件有查看器从未加载的行，而只把已持有的页写回去会删掉它们。查看器对这种文件——以及仍在读取的文件、读取失败的文件——以一句说明原因的话拒绝，而不是按需补全读取：那种替代方案会让编辑按钮的含义取决于一次本身可能失败的异步读取，而拒绝是一个状态而不是第二套流程。

**末尾换行是重建的，不是猜的。** 一页用 `\n` 连接各行并丢掉最后一行的终止符，所以单看页文字分不出 `a` 与 `a\n`。store 保留 Host 报告的文件字节大小，并与页文字自身的 UTF-8 长度比较：相等即没有丢东西，不等即补回一个换行。用 `TextEncoder` 度量是因为浏览器里没有 `Buffer`。Host 不报告大小时文字按读到的原样使用，这是诚实的降级。

**拒绝保留读者的文字。** 草稿——基线、当前文字、以及读到时所属的版本——住在该 tab 的 store 桶里，于是编辑器能挺过 store 的重渲染，失败路径也有地方让文字保持原样。保存进行中时按钮禁用，与基线相比没有变化时也禁用，于是空操作保存是被「不提供」而不是被发出后再忽略。重新载入会连同页一起丢掉草稿，因为它带回来的页属于另一个版本，草稿的保存本来也会被拒。

## Alternatives considered

**按页或按行区间编辑，而不是整个文件。** 局部写入需要在线路上带一套补丁词汇（偏移、长度、期望内容），还需要区间移动时的合并方案；整文件替换只需要一个版本和一个字符串。分页读取的存在是为了给大文件的内存占用设界，而「查看器已完整持有的那一个文件」这个编辑范围让这个界保持诚实：查看器持有的从不超过 Host 的页上限，而写入由同一个 `maxBytes` 设界。

**点编辑时自动加载剩余各页。** 它让按钮对每个文件都能用，代价是在编辑手势里塞进第二套异步流程——一个进行中状态、一个失败状态，以及加载失败时按钮该怎样的决定。拒绝只是一次渲染和一句话。

**用 `mtime` 或大小做乐观并发。** 两者都比后端的版本令牌更粗，而且本来就是同一个值的输入；服务等于在重新推导文件系统 seam 已经发布过的令牌。

**把保存接到 Agent 的写工具或其瀑布上。** 上文已述：策略对非工具 actor 的契约使它无法用于覆盖，而伸手去伪造一个 Session actor 就是绕过一道关，而不是穿过它。

**为编辑器开一个新的 tab 种类。** tab 系统把内容身份绑定在地址上，而同一个文件的编辑器是同一份内容的另一种模式。第二种 kind 会让一个文件拥有两个对它的文本各执一词的 tab。

## Consequences

右侧栏现在闭上了它打开的那个环：读文件、改一行、保存、看到结果，全程不离开 harness。所有失败模式都是可见的而非静默的——版本过期、写入过大、文件过于残缺无法编辑、Session 不允许写——每一种都说明发生了什么，同时保留用户的文字。

有三条限制记在包的 README 里而不是在这里解决：写入只能整文件（没有补丁、追加或按区间写入），分多页读取的文件完全不能编辑，关闭带草稿的 tab 会不问自弃。每一条都是未来可以补上的真实缺口，而没有一条会丢掉磁盘上已有的数据。

版本守卫用的就是文件自己的 `FsVersion`，所以没有新存任何东西：这次写入与 Agent 工具执行的是同一种带守卫的替换，只是走了非工具调用方拥有的那条缝。这个服务将来若长出别的变更操作，应当复用它，而不是另造一个并发令牌。
