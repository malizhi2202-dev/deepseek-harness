# Agent Note：QQ 与微信聊天渠道提供方

Status: implemented

[English](2026-09-22-qq-and-wechat-chat-channel-providers.md) | 中文

## 问题

聊天渠道缝隙让聊天平台可以驱动一个 Session，而运营方需要在企业双雄之后，再接入他们团队最常用的两个平台：QQ（QQ 机器人开放平台）与微信（微信）。这两个平台在本仓库中都没有传输层，也都没有本仓库可依赖的 Node SDK：能够触达它们的第三方包（`wechaty`、`wechat4u`、`qq-official-bot`）各自独占进程的消息循环、只服务一个账号，并把登录二维码渲染到终端——对于要同时保有多份绑定、并把二维码送进浏览器的宿主而言，这是错误的形态。

两个平台性质决定了整个设计。QQ 每次调用都用一枚短期访问令牌认证，而凭据对只用来换取它；并且它只允许把发送作为对近期入站消息的被动回复，且受一个很小的单条消息配额限制。微信的入站是服务端挂住的长轮询，这正是该渠道在没有公网地址时也可行的原因；它的登录是一枚携带一次性登录令牌的二维码。

## 决策

两个提供方包加入该缝隙：`packages/channel/channel-qq`（`@deepseek-ai/dsh-channel-qq`）与 `packages/channel/channel-wechat`（`@deepseek-ai/dsh-channel-wechat`）。每个都是导出 `name` / `inject` / `Config` / `apply` 的函数插件，注入 `chatChannels` 与 `credentials`，声明一个设置命名空间（`chat-channel-qq`、`chat-channel-wechat`），并为其配置段命名凭据引用字段。两者都注册进 `dsh-web-app` 组合。

**两套协议都按腾讯公布的端点自行实现，且都没有引入依赖。** Node 22 提供全局 `fetch` 与全局 `WebSocket`，而那个 `WebSocket` 正是参考实现点名要用的 undici 实现，因此使用全局对象是等价而非降级。QQ 的网关、它的令牌交换、微信的长轮询，以及微信的媒体下载，因此全部建立在平台全局对象加 `node:crypto` 之上。

### QQ

- **访问令牌由客户端缓存并刷新，而不是由调用方操心。** `packages/channel/channel-qq/src/token.ts` 为所有调用方持有一枚令牌，把并发的突发请求合并为一次交换，并在其声明到期前 60 秒替换该令牌——这正是平台记录的轮换窗口。被平台的无效令牌码拒绝的调用会使缓存失效并重试一次。
- **回复额度是上报的，不是强制的。** `capabilities.replyBudget` 为 4，即平台的单聊每条消息 4 条回复与群聊 5 条之中更紧的那个，而真正把回复控制在额度内的是桥接层自己的封顶。在提供方里再强制一次，等于让同一个决策有第二处可能出错的地方。
- **序号与回复窗口由提供方拥有。** `packages/channel/channel-qq/src/replies.ts` 记住每条入站消息，按认领分发 `msg_seq`，并在五分钟后让条目过期。当会话中没有可回复的消息时，`sendText` 与 `replyText` 以 `ChatUnsupportedError` 拒绝，因为平台并未提供本连接器所实现的主动推送。
- **平台文档在单聊窗口上自相矛盾。** 同一页中，一个字段的正文写五分钟，而表格写六十分钟。提供方采用更紧的那个读法，因此它绝不会声称一条平台可能拒绝的回复。

### 微信

- **入站是长轮询。** `getupdates` 由服务端挂住，直到有消息到达或窗口关闭，因此该连接器不需要任何入站地址。
- **每个会话都是单聊。** 平台的机器人通道是一对一的，因此连接器对每个会话都上报 `direct`，并以对端的 openid 作为接收 id。
- **出站消息必须携带该会话最后一条入站消息的 `context_token`。** 连接器维护一张有界的令牌表，对从未发过言的会话、或令牌已被淘汰的会话，直接让发送失败，而不是不带令牌发送。
- **媒体类型是从下载到的字节中嗅探出来的**，因为平台并未声明它；而分段上限来自官方客户端自身的文本限制，而不是某个有文档的服务器上限。
- **登录是一枚密钥等价的二维码载荷。** 它内嵌一次性登录令牌，因此任何读到它的人都能把一个客户端绑定到该账号。提供方获取它，按平台自己的超时语义轮询到结束，并上报一个可辨识的结局——`confirmed`、`expired`、`blocked`、`already-bound`、`verification-required`、`timeout` 或 `cancelled`——同时上报每一次替换后的挑战，并在平台要求时请求验证码。它从不渲染该载荷，从不记录它，也从不把它放进错误消息。

### 注册渠道 id，以及掩盖了它的两处静默失败

渠道 id 映射是可合并扩展的，每个提供方都在自己的 `src/types.ts` 中通过增强 `@deepseek-ai/dsh-channel/types` 加入自己的键。这需要两个条件同时成立，而破坏任何一个都是静默失败：联合类型只是缺少那个键，在某个调用点把它钉住之前不会有任何报错。

1. **被增强的子路径需要自己的 `paths` 条目。** `tsconfig.base.json` 的生成别名区只映射裸包名，而且映射到 `src` 目录而不是某个文件。若没有为 `@deepseek-ai/dsh-channel/types` 手写的条目，该子路径会经由包的 `exports` 解析到已构建的声明，那是与源平面程序所读的实例不同的另一个模块实例，于是合并落在无人查看的地方。该条目现在与其他手写子路径条目放在一起。
2. **被增强的模块必须从包入口可达。** 空的 `import type {} from './types.ts'` 无法让该模块留在每个到达入口的程序中，而 `export type * from './types.ts'` 可以——这正是缝隙自身入口已经在用的形式。

对注册表列表做 `toEqual` 抓不到这两处失败中的任何一个，因为它对期望值是泛型的；真正钉住合并后联合类型的是按字面 id 的查找，因此 `chatChannels.get('qq')` 及其同类现在会断言它。这两处失败在四个聊天渠道提供方中都存在，并已一并修正。

## 考虑过的替代方案

**依赖第三方客户端。** 拒绝的理由是形态而非许可：它们各自独占进程的消息循环、只服务一个账号、把二维码渲染到终端，并把状态保存在 dotfile 中，这些都不适合同时保有多份绑定的宿主。官方协议是公开的，不需要这样的包。

**为它的 `WebSocket` 直接把 `undici` 作为依赖引入。** 拒绝：Node 的全局 `WebSocket` 就是同一个实现，因此该依赖删不掉任何代码。

**在提供方里强制回复额度。** 拒绝：桥接层已经为回复封顶并构建分段，因此第二个强制点会让同一个决策有第二处可能出错的地方。提供方上报额度，只拥有平台归于消息本身的那部分。

**不带 `context_token` 发送微信消息。** 拒绝：平台把一条回复绑定到发起它的那条消息上，而不带令牌发送将是对一条无文档路径的未经验证请求。

**给授权能力添加 `qr` 种类。** 推迟，而非拒绝。二维码载荷是密钥等价的，属于授权路径而不属于普通面板文本，但拓宽一个已交付能力的提示联合类型及其客户端本身就是一项独立变更。在此之前，连接器把登录作为其自身连接器类型上的一个带类型额外成员暴露出来，从而让授权包与冻结的缝隙保持不动。

## 后果

- **五个渠道可以驱动一个 Session，而桥接层对它们一无所知。** 去重、会话锁定、接纳、出站转发与回复文件投递都留在一处。
- **远端控制面板无需任何客户端改动就列出全部五个。** `apps/web/tests/snapshots/sidebar-channels/panel.expected.md` 被重新录制，因为装配后的组合现在服务五个连接器；面板自身的代码未被改动，而它绘制的是每个平台声明的能力与设置字段。
- **QQ 无法开启对话。** 每次发送都是被动回复，而主动推送有自己的配额与审批策略，因此近期没有发过言的会话无法被发送。此项记录在该包的 Known Limitations 下。
- **一个回复额度覆盖了两个平台额度。** 群聊会少用一个回复的余量。
- **微信登录尚不能从面板触达。** 连接器暴露了该流程及其结局联合类型；显示该载荷需要那个被推迟的提示种类。
- **没有对任一平台发起真实 API 调用**，因为这里不存在可用的应用。每一条线上事实都来自平台公布的文档，而每个套件都驱动一个打桩的传输层。
- **`pnpm run duplication` 在本机无法运行。** 钉住的 jscpd v5 二进制需要 GLIBC 2.32 或更新，而本机提供的是 2.31。以相同阈值经 jscpd v4 的 JavaScript 构建对每个渠道提供方的 `src/` 运行过，报告无克隆，但必须由 CI 用真正的门禁确认。

## 测试

`packages/channel/channel-qq` 有 109 个测试，`packages/channel/channel-wechat` 有 104 个，两者在逐文件 100% 的语句、分支、函数与行覆盖率上均达标。套件钉住了令牌缓存的复用、其轮换边界、字符串类型的 `expires_in`、并发调用方只触发一次交换，以及失效并重试；回复账本的序号、最新消息优先规则、精确到期与淘汰上限；微信长轮询循环、`context_token` 表的边界、媒体嗅探，以及在其精确上限处的 markdown 降级；二维码流程的启动、轮询、刷新、验证码与取消路径；以及 `apply` 恰好注册一个连接器——通过按字面渠道 id 的查找来断言。`apps/web/tests/sidebar-channels.e2e.ts` 启动装配后的组合，并钉住全部五个连接器所产生的面板。
