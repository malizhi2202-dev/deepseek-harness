# repair-subagent — 子议题拆解

议题：一次失败之后，如何派生一个修复者（agent / job / run），以及今天缺什么。

本议题由 `../sidebar-asks-2026-09-17/` 的右侧栏诉求拆出，属于「失败之后能做什么」这一族。上游 `../failure-attribution/` 已收口「失败如何被归因与呈现」，本议题接在其后，处理「归因之后能不能动手」。

## 本轮约束与方法偏离

- 循环全程**只读**：未创建、修改或删除任何文件，未读 `/tmp`；文档在人工审核门通过后落盘。
- `bmad-discovery-loop` 的第五步（人工审核门）在对话中完成，落盘发生在门后，与技能「审核通过才落盘」一致。
- 子代理按 `bmad-deep-recon` 默认流程应建 run folder / digest / memlog；只读约束下不写盘，证据只存在于回传正文。**属偏离**，记录在 `06-review-record.md`。
- `web_search` 在本环境不可用，外部证据一律用 `web_fetch` 直连权威源，并带逐字英文引文。

## 已确认的上游结论（不重开）

- 失败归因不需要新增会话事件；不加布尔；不给 `turn/end` 加 step 坐标；`step/end.outcome` 排队；`authority` 随它走。
- 动作面已定：动作是既有面板上的一层，不新开面板；改会话状态的走命令路径，移动视口的走类型化客户端调用；主体由宿主解析，绝不接受客户端自报。
- 上游遗留项「必须落域事件是门还是刹车」在本议题内**不构成阻塞**（门内裁决见 `99-implementation-checklist.md`）。

## 门内三条裁决（人工审核门给出，本议题据此落盘）

1. 修复者首发默认刻度为**只读**；需要写时**必须人类同意**。
2. **派生动作用本身是危险动作**，因此必须人类确认，且**不能走命令路径**。
3. 上游未决项**不先收口**，不作为本议题的前置条件。
