# 04 · 结论与建议

**一句话结论：DSH 今天不存在「从失败派生修复者」的机制。本议题的主体不是加一个按钮，而是补一条新的委派路径；工作量属第二档（需新写入端，但不改事件契约），且入口在结构上不能是命令。**

| # | 事实 |

## 二、推荐（按序）

### R1 · 失败上下文包 + 只读接力（先做）

- 上下文包＝**结构字段 + 必填的具名未知项**，模板照 F8；坐标引用（会话、turn、step、事件 seq）优先于正文转发（J8、E8）。
- 首发修复者**默认只读**：给结论与建议，不改工作树。只读由**组合层工具过滤**落实（J13），单调工具守卫兜底（J11 同族）。
- 必须**保留原失败 run 的日志与状态**，不得按 E19 的语义把失败证据处理掉。
- 首发的触发方式是**人类确认过的派生**（门内裁决 2）；模型可以提议，不能自行提交。

### R2 · 入口走会话内人类手势，不走命令路径

- 照 J3 的不可伪造手势与「两个独立开关」：人类侧与模型侧作为**两个独立注册的能力**。
- **主体由宿主解析**，绝不接受客户端自报（J5）；措辞与形状参照现成的 `SubagentInterruptAuthority`（J2）。
- **R2 的审计落点需另行设计**：门内裁决 2 要求人工确认，而 F4 禁止把审批放进命令路径 ⇒ 审计不能靠「包成一条命令」获得（见 V2）。

### R3 · 权限与预算边界

- **R3a（随 R1 一次带上）**：显式次数与预算，复用 J11 的既有闸门；写明冷恢复不继承预算（F10e）。
- **R3b（等真实压力再做）**：补上按父级并发上限（J12）；写类能力一律落在人工确认之后，且**发起派生的一方不得自批**（E2）。

### R4 · 排队项（唯一格式级）

- 给描述符加「失败来源」输入属版本变更（J7b），且只覆盖描述符、不覆盖会话事件；**等第二个消费者**。

## 三、门内追加的事实对推荐的影响

- **J9/J10 把「首发只读」从风险取舍变成结构事实**：审批在子代理里必然被拒，所以任何需要审批的写今天在子代理内**不可能成功**；而沙箱内的写又不需要审批。两条合起来意味着「只读」必须由**主动限制**（工具过滤 / 守卫）保证，不能指望审批兜底。
- **J13 把「只读存哪里」的问题消解**：可续跑描述符已经带 `toolFilter`（与 `persona`、`agentModel` 同级），**零格式变更**即可持久记录；一次性描述符只带 `label`（F7d），其只读只是组合层设置、子代理自己的日志里查不到——这是 R1 的一个已知不对称。
- **J14/J15 把可见性问题定形**：模型侧派生今天已经是 surface 事件（工具调用与其结果）；**人类侧派生写的是子日志、父会话零事件**。因此「父模型要不要看见这次派生」就是那个决定是否格式级的问题。

## 四、否决记录

| 编号 | 否决项 | 理由 |
| --- | --- | --- |
| V1 | 把「派生修复者」做成一个新按钮 / 新面板 | 动作面已定：动作是既有面板上的一层；且本议题的真问题是委派路径 |
| V2 | 走命令路径来获得审计 | F4：命令装不下审批；把纯读包成命令会造出**假审计**（上游已判） |
| V3 | 让现有委派工具自我递归来修 | 绕过预算与审计语义；委派参数里没有预算旋钮（F6 附近的参数面） |
| V4 | 今天就给描述符加「失败来源」字段 | J7b：唯一格式级项，且无第二消费者 |
| V5 | **自动**派生（模型自行提交修复者） | E3/E12：没有任何系统声明该规则；最强先例要求发起者不得自批；门内裁决 2 亦否 |

## 五、交给 ⑤ 的三条必答项

1. 「只读」如何强制（载体已存在，缺的是禁哪些工具、谁来配）。
2. 人类触发的派生是否需要父模型可见 ⇒ 决定是否引入 session surface 事件（格式级）。
3. 宿主侧主体解析的具体设计（F5 的客户端自报不可照抄）。
