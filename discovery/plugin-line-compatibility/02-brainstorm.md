## 二、方向与既有事实的碰撞（本议题溶解的直接原因）

- **D13 撞上 F12**：挂起状态**已经可见**（既有插件设置页逐入口显示根纤维阶段，含 `pending`）⇒ D13 不是待做项，只剩**成因**那一格（F13）。
- **D14 撞上 F3 + F10 + F11**：`dsh` 是共享词表、**每个读者自负校验**，且解析器只丢未知键。做一个全命名空间的「未知字段」报告器，必须取得**全命名空间所有权**，否则会把别的读者拥有的键误报为未知。
- **D5/D6 撞上 F8 + F9 + F19**：加载期未必拿得到插件清单（`locatePkgJson` 可返回 `undefined`），且第三方 client 插件经 bundle 行与回退解析进入；安装期则**没有落点**（本仓无市场实体，唯一插件状态面自述无变更路径）。
- **D1/D5 撞上 F15 + F16**：朴素的版本判定会先把**当前树自己所在的那条线**判为不兼容（`^0.1.2-rc.1` vs `0.1.3-alpha.2` = false）。
- **D4 撞上 F17**：两条安装路径的 peer 设置不一致，任何依赖 peer 行为的门都要先说明自己在哪条路径上。

## 三、反例

**主张「把目标线字段收进词表并 fail-loud 一定更好」**：① 等于为一个本仓从未执行、语义未定的通道背书，误判后果从「装上了但面板不显示」升级为「整个 profile 起不来」；② 核心只在自己读的通道上 fail-loud，覆盖的只是**守规矩的子集**，而漂移到无人执行通道的恰是更该拦的那批。

**主张「校验应放在最早的加载期判定点」**：① 加载期未必拿得到那份清单（F8 可返回 `undefined`；F9 表明第三方 client 插件不在 bundle 层）；② 加载期 fail-loud 命中时用户已装完、重启即失败，而安装期判定虽能挪到可回滚处，却拿不到检出树的真实版本——**没有哪一层天然免疫**。

**主张「用朴素 semver 判兼容就够」**：① 核心**正常前进一格**就把合法插件判死（F15 第三组）；② 本仓检出线恰落在被判 false 的那组里（F15 第一组 + F16）⇒ **判定本身先错，fail-loud 只是把错误放大**。

**主张「静默失效必须变成立即中断」**：① 挂起是既有语义（F5），改成超时中断会同时改变**所有合法等待注入的插件**的行为；② 需要可见的是「装了没生效」，而挂起只是成因之一——bundle 行漏挂、依赖未声明同样致命（F9 已列出多个「在更晚、不同点失败」的注册面），只盯挂起会把其他成因继续留在静默里。

**主张「加校验不会伤害生态」**：① F17 的漂移方向意味着核心此刻加门会**挡住仍写 peer 的老插件**、放过新写法的插件——罚了合作者；② F18 的历史顺序是「先批量禁用、后补装入即验证」，若先上强制校验，会把当年的批量禁用变成**批量启动失败**，用户回滚成本更高。

## 五、三个最危险的假设

1. **「未声明目标线 ＝ 兼容」这个默认值**：向后兼容的诱惑会让校验器放行所有未声明的包，于是**已声明旧线**的插件与完全没声明的插件被同等对待，而「声明了却对不上」恰是最该拦的一类。表现为校验给出虚假安全感，且在核心升级时才暴露。
2. **「加载期一定读得到插件清单，所以校验必然生效」**：F8 的返回值可为 `undefined`，F11 表明未知字段**连被丢弃都不会被记录**。一个读不到字段的校验器会**空转通过**，输出看起来和校验成功一模一样。
3. **「核心单调前进、插件被动跟随即可」**：F16 表明核心也可能比插件新。把「核心更新」一律判兼容，破坏就只在运行时表现为面板静默消失，没有可归因信号。

**附带假设（同源风险，不计入三条）**：**「两条安装路径行为一致」**——F17 记录了两条路径的 peer 设置不一致。任何依赖「peer 会被装上」或「peer 一定不装」的设计，都需先确认自己在哪条路径上。

## 六、交给 ③ 的未决问题

1. 目标线字段是否成为共享词表的正式成员？——归属**词表所有者**（对应 D1、F1、F2）。
2. 校验的失败模式默认是阻断还是警告？若阻断，「必须跟着核心升级」的成本由谁承担？——归属**产品/发布负责人与核心线维护者共同签署**（S5 全部方向）。
3. 第三方 client 插件的清单在加载期是否可稳定读到？——归属**客户端加载/模块图所有者**，且必须先给出可复现的路径级证据（F8、F9）。
4. 兼容判定采用哪一套语义、由谁拥有一份可执行的判定表？——归属**核心版本/发布负责人**，F15 的四组应作为准入用例。
