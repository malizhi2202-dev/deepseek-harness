# 插件目标线兼容：③ 结论与建议

**一句话结论：本议题不是「缺少强制」，而是「声明不可见」与「失败成因不可见」两重问题；而在补上一步核查后发现，「失败可见」这一环已经是既有能力，故本议题判为溶解，只把可落地的部分移交。**

## 一、判定溶解的那一步核查

专家团建议把「让挂起的插件可见」作为本议题唯一可以立刻做的事。核查后发现该能力**已经存在**：

- 既有只读插件状态投影逐入口返回根纤维阶段，**阶段枚举里包含 `pending`**（F12）。
- 且**已有面向用户的设置页客户端**消费该投影（F12）。
- 但入口行只有四个字段，**不含未满足依赖明细**（F13）；底层加载器**也不暴露未满足注入名**（F14）。

⇒ 「装了但没生效」在用户侧**已经看得见**（显示为挂起）；**看不见的只是「为什么挂起」**。

## 二、修正后的现状

| 环节 | 现状 | 依据 |
| --- | --- | --- |
| 失败可见 | **已有**：挂起状态在既有设置页可见 | F12 |
| 失败成因 | **缺**：不说是哪个注入没满足 | F13、F14 |
| 声明归属 | **不是本议题的**：清单是共享词表，每个读者自负校验 | F1、F3 |
| 加载期阻断 | **已被证伪**：朴素的版本判定会先把当前树自己所在的那条线判为不兼容 | F15、F16 |
| 安装期判定 | **无落点**：本仓无市场实体，唯一插件状态面自述无变更路径 | F19 |
| 未知字段报告 | **无落点**：需要全命名空间所有权，否则会把别的读者拥有的键误报为未知 | F3、F10、F11 |

## 三、外部规律（10 个生态，详见 `03-competitive-recon.md`）

1. **强制程度由「谁承担错误安装的代价」决定**，宿主自己完成解析/安装/激活的一律强制，其余四种成因归于「质量声明」「消费者是第三方目录」「best-effort 可降级」「越权代价高」。
2. **上限字段少见有机制原因**：宿主默认向前兼容是策略、有的生态上限默认即关闭检查、有的由版本范围本身表达、有的结构上写不了。
3. **「装错版本」的行业解法是回退到兼容版本**，而不是拒绝 ⇒ 判定点天然在市场/安装侧，不在宿主加载期。
4. **依赖未满足应当显式浮出**；**能力探测优于版本比较**。

## 四、建议（按专家团最终排序，含主 agent 的两处更正）

| 序 | 建议 | 处置 |
| --- | --- | --- |
| 1 | **R1「让挂起可见」** | **已被 F12 取代**：既有能力已覆盖，本议题不必做 |
| 2 | **R3「目标线字段的归属与语义」** | **移出本议题**，移交共享词表所有者；且不能只加字段，必须同时定「只写下限还是可写上界」的语义，并解掉「共享词表 vs 权威 schema」的措辞张力 |
| 3 | **R4「安装期判定」** | **只留一行登记并移交**，不在本议题内实现（落点见 F19） |
| 4 | **R2「未知清单字段报告」** | **降级为可选，本议题不实施**（需要全命名空间所有权，见 F3/F10/F11） |
| 5 | **R5「加载期阻断」** | **冻结**，附复活条件：**若将来改为能力探测而非版本比较，则可做** |

**幸存项移交**：`pending` 的**成因**可见性（F13、F14）。它需要一个新的探测面（加载器目前不暴露未满足注入名），不属于本议题的声明/校验范畴。

**语义建议（供移交对象参考，不在本议题内实施）**：匹配规则必须收进**单个纯函数、单点拥有**，并以 F15 的四组实测为**准入用例**；候选规则是「只比较声明线的主流版本段、忽略预发布标识符」的**只写下限**规则。

## 五、不重开与不做

- **任何方向都不需要改动会话格式（明确为 0）**。
- **不改挂起语义**：改成超时中断会同时改变所有合法等待注入的插件的行为。
- **不引入上限字段**：外部规律 2 给出了机制原因。
- **不在本议题内决定目标线字段是否进词表**：归词表所有者。
- **不做「先加个版本检查试试」**：F15 与 F16 已证明第一个判决就是错的。

## 六、三问的裁决（门内「依你的建议」，2026-09-17）

1. 幸存缺口「挂起成因」→ **并入既有插件设置页议题**，不在本议题内立项。
2. R2 与 R5 的否决 → **接受并记录**，附理由与复活条件（`99-implementation-checklist.md` 的 X1、X2）。
3. 目标线字段 → **以移交便条形式记录，不主动推进**（H2，含语义与措辞两项前置）。
