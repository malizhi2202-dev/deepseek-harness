# 工作区定时对齐：需求与已核实事实

负责人原话（三条，后两条为补充）：

> 1 给每个工作区维度添加一个定时器模块
> 2 这个模块的作用就是定时 对齐git 以及git内的文档、pr、提交、代码 定时合并对齐 调研下其同类产品咋对齐的落地方案和代码
> 3 在添加 在每个工作内部自动总结 自动提交commit 但是push 由人决定

因此本议题有三个交付物：**一个按工作区维度存在的定时器模块**；**它的作业之一——把 git 及其内部的文档、PR、提交、代码做定时合并对齐**；**它的作业之二——在每个工作内部自动总结并自动提交 commit，而 push 由人决定**。并且要**调研同类产品的落地方案与代码**并写进该模块（调研稿见 `01-competitive-landscape.md`）。

### 负责人裁定：PR 对齐本轮明确不做

原话要求里点名了「pr」。实查**全树没有任何 forge 写能力**——没有 `@octokit/rest`、没有 `@octokit/graphql`；唯一的 GitHub 依赖是 `webhook-github` 的 `@octokit/webhooks`，它**只做入站签名校验**，不能列 PR、读状态、改 base、更新分支或入队。因此 PR 对齐的前提是先造一个 GitHub API 能力（新接缝 + 鉴权 + provider + 测试），是一块独立的、不小的成本。

**负责人裁定（2026-09-22）：只做本地 git 对齐，PR 明确不做。** 接入时必答的前置问题（例如「Update branch 会作废人工审批」）已记录在 `01-competitive-landscape.md` §1.2 与设计稿中，实现留待将来。

## 一、需求拆解（含必须向负责人确认的歧义）

| 要素 | 字面要求 | 歧义/待定 |
| --- | --- | --- |
| 维度 | **每个工作区**一个 | 已核实工作区是**持久记录**（`WorkspaceRegistry.get/list`，`Workspace` 带品牌 `WorkspaceId` 与规范目录路径）。所以是"每个 Workspace 记录一份定时配置与状态"，不是每个 session |
| 定时器 | 定时触发 | 间隔？是否可配？是否持久（重启后是否补跑）？ |
| 对齐对象 | git 本体 + **其内的文档、PR、提交、代码** | "PR" 不在本地 git 里——它要求**代码托管平台 API**（GitHub 等）。本仓库当前**没有**任何 forge 能力。这是本议题最大的范围缺口，见第四节 |
| 动作 | **合并对齐** | 快进？合并？变基？冲突怎么办？这是安全性的核心，见第五节 |
| 调研 | 同类产品**落地方案和代码** | 已交子代理调研中 |

## 二、已核实：本仓库现有的"定时"与"后台作业"底座（都不合用）

| 能力 | 真实定位 | 为什么不合用 |
| --- | --- | --- |
| `packages/schedule/schedule` | **会话内**持久提醒：`schedule_create/list/delete` 工具，到期作为**同一会话的后续消息**投递；一次性（延迟或绝对时刻）或固定间隔重复；重启后仍在 | 归属是 **session**，投递物是**一条会话消息**。本需求归属是 **workspace**，产物是**文件系统/git 状态变更**。维度不同，不能当底座 |
| `packages/jobs/jobs` | **后台作业**注册表契约：稳定 `<kind>-N` id，agent 可读输出/等待/取消；**作业属于启动它的 agent 会话**，一个 agent 的工作对另一个不可见 | 归属同样是 **session**（"jobs belong to the agent session that started them"）。工作区级作业不属于任何会话 |
| `packages/client/ui-schedule` | Web 头部**只读**的提醒目录 | 只读展示，非调度器 |

**结论**：本仓库**没有**工作区级、宿主级的周期作业底座。这不是"重造轮子"，是真实缺口——但**定时机制本身**（持久化、重启后补跑、到期判定）在 `schedule` 里有成熟实现，设计时必须先读懂它的持久化与到期模型并复用其机制，只换归属维度，不重写定时算法。

## 三、已核实：git 能力目前是**只读**的

`packages/git/git` 的服务定义只有**一个**抽象方法：

```ts
abstract observe(cwd: string, signal: AbortSignal): Promise<GitObservation>
```

`GitObservation` 是**有界只读快照**（分支、HEAD、index 状态、有界历史）。全树**没有** `fetch` / `merge` / `rebase` / `commit` / `checkout`。

**这是本议题第二个硬缺口**：定时对齐必须做**写操作**（取回远端、判定 ahead/behind、快进或合并、冲突时停手）。设计上要在两条路里选，并说明理由：

1. **给 `git` 接缝加写方法**——但它的契约自述是"有界只读观察"，且其 Agent Note 把它记为**有期限的临时配套**（"随替换它的上游 git 插件一起退役"）。改契约要正面回答：只读是不是它存在的理由。
2. **另立一个对齐接缝**（如 `ctx.workspaceSync`），provider 经既有 subprocess/shell 能力执行 git 命令，把"git 命令知识"留在 provider 而不是消费者。按仓库约定「provider 专属行为留在 provider 或消费者，不让一个消费者决定服务契约」，这条更顺。

## 四、范围缺口：对齐 "PR" 需要 forge 能力（本仓库没有）

本地 git 里没有 PR——PR 是托管平台的对象。要"对齐 PR"，至少需要：列 PR、读 PR 状态、改 PR 的 base、触发"更新分支"或入队合并。本仓库当前**没有任何** GitHub/GitLab 能力包。

可选路线，需负责人定夺：

- **只做本地 git 对齐**（远端取回 + 本地分支对齐），**不碰 PR**——范围最小、无新依赖、无凭据需求。
- **接 forge API**（`@octokit/rest` 已在树内被提及可用）——范围大、需要凭据（走既有 `dsh-credentials`）、且"自动改 PR"是**对外可见的写操作**，风险等级远高于本地合并。

在负责人给出取舍前，设计按"只做本地 git 对齐"为默认，把 PR 对齐列为明确不做的部分并写明原因。

## 五、安全性：定时自动合并是本议题最危险的一处

按仓库约定「**在做出决定的那次操作里强制**」与「误配要响亮失败」，设计必须正面回答：

1. **绝不静默解冲突**。冲突时停手、保留现场、如实报告——不猜、不 `-X ours`、不丢弃任何一侧。这条是硬底线。
2. **默认是"观察并报告"而不是"自动改"**。周期动作先产出"落后 N 个提交、可否快进"的判定；**写操作需要显式启用**。这与同类产品的实际做法一致（调研稿会给出证据）。
3. **工作区可能有未提交的改动**。定时器在脏工作区上做合并会破坏用户正在做的事，必须有前置判定与拒绝路径。
4. **不做破坏性操作**：不 `reset --hard`、不 `clean -fd`、不强制推送、不重写已推送的历史。
5. **有界**：单次操作的时间上限、并发上限（同一工作区同一时刻只有一个对齐在跑）、失败退避，避免定时器变成风暴。
6. **可观测**：每次对齐的结果（做了什么、为什么没做、冲突在哪）要能被用户看到，不能只写日志。

## 八、第三个交付物：自动总结 + 自动提交（push 由人决定）

> 3 在添加 在每个工作内部自动总结 自动提交commit 但是push 由人决定

这一条与第二条共用同一套缺失底座（可变的 git 能力、工作区级的触发面），但它的**危险点与第二条不同**，必须分开设计。

### 8.1 已核实：可复用的与不存在的

| 事项 | 实查结果 |
| --- | --- |
| 自动提交 | **全树不存在**。`grep -rl "git commit\|autoCommit" packages/` 无命中 |
| LLM 总结的接缝范式 | **已存在**：`packages/session/session-title` 是接缝（`SessionTitleProvider { generate(request) }` + `SessionTitleService`），并有 `session-title-llm` 等 provider，自动模式 `'first-prompt' \| 'all-prompts'`。**总结机制可复用其范式，但它产出的是会话标题（短标签），不是变更摘要** |
| `session-turn-outline` | 是**轮次导航**数据（`turn/start` seq + 有界预览），供聊天轮次导轨用。**不是工作总结**，不可当摘要复用 |
| "这一轮产出了哪些文件" | **已存在**：`ui-deliverables` 与 produced-files 记录了一轮结束时产出的文件；远端控制议题里"只投递本轮**真写过**的文件（mtime ≥ 本轮开始）"用的就是同一条判据 |

### 8.2 粒度歧义（我的默认，可否掉）

"每个工作内部"有三种读法：**每个工作区**（与第一条一致）、**每个会话**、**每个工作单元（一轮 turn / 一次作业）**。我的默认是**每个工作单元**——因为"自动总结 + 自动提交"天然以"一段工作做完了"为界，而 `turn/start` 是本仓库已有的边界事件。若负责人指的是"每个工作区攒一批再提交"，改一个触发条件即可，不影响其余设计。

### 8.3 最危险的一点：自动提交会把什么固化下来

合并冲突是"当下出错"，而**自动提交是"把错误永久写进历史，而且人随后可能 push 出去"**。因此：

1. **绝不 `git add -A` / `git add .`**。只提交**本次工作真的写过的路径**（复用 produced-files / mtime 判据）。用户自己的半成品改动、无关文件、生成物一律不进这次提交——这是本条的**核心安全属性**，不是体验细节。
2. **提交前做密钥筛查**。工作区里可能有 `.env`、凭据文件、私钥；一次自动提交会把它们固化，而 `push` 是人来决定的——人可能不看内容就推。命中即**拒绝提交并报出路径**（只报路径，不回显内容）。
3. **提交信息由总结生成，但事实来自 diff**：总结不得声称没发生的事。生成失败时**退回机械摘要**（改了哪些文件、增删行数），绝不编。
4. **不做破坏性操作**：不 `--amend` 已推送的提交、不 `rebase` 已推送的历史、不改写作者身份。
5. **push 永远是人的动作**：本模块**不提供**任何自动 push 路径。它只负责把提交准备好，并把人需要的信息摆出来（提交了哪些、还有什么没提交、为什么没提交）。这条是负责人明确要求的边界，也是最该被测试覆盖的边界。
6. **可撤销**：提交是本地对象，人未 push 前可以撤回；因此报告里必须给出撤回方式（重置到哪个提交），而不是让人自己找。

### 8.4 待调研补充的问题

调研稿需额外回答：同类产品里有没有"自动提交但由人推送"的真实系统（IDE 的 local history、AI 编码工具的 auto-commit、`jj` 的自动快照、`git-autocommit` 类工具）？它们如何界定"提交什么"、如何处理密钥、提交信息从哪来、如何让人放心？
