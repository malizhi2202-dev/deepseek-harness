# R3-2 ③ 结论与建议

**裁决：有界**，唯一硬代价是格式换代不可逆。

**数值**：格式换代 1 次（2→3，向前迁移边齐全）；SQLite 域变更 **0**；核心包 **157→163 只增不减**；运行时必需包树内齐备；该 profile 的 disabled 插件多数属同一 `@linxin666` 家族，可批量处理。

**"迁移"的具体含义**：在这棵树上 = fetch fork 的 master（`47f9438`）再在本地开发分支上 **rebase**（携带一条未推送提交 + 一批未提交改动）；不是"换个版本装一下"。

**理由摆正（专家团要求）**：**被甩下的是这棵树自己**，不是"救插件" —— 上游插件已跑到 `^0.1.5-rc.1` 线。

**最小步骤**（含主 agent 的更正）：
1. 先备份 sessions、storages 与 profile 配置。
2. 新建独立 profile（如 `web-015`）—— **但它只隔离插件与组合接线**。
3. 提交或 stash 未跟踪的 `ui-sidebar-tasks` 与未提交改动，再 rebase。
4. 只在新 profile 装新线依赖（better-sidebar `^0.19.1`、checkpoint-rewind `^0.6.11`），其余保持 disabled，重建 `.dsh-module-fallback`。
5. **用独立 `DSH_HOME` 整份副本**验证老会话可打开（不能只换 profile）：把 sessions+storages 拷进去跑；确认"新线**打开** v2 会话是否就会写出 v3 后继文件"——若会，则"只读验证"不成立。
6. 再切到主实例并观察 1–2 天。

**回滚故事（诚实版）**：代码可回退（分支与旧 profile 都在），但**任何被新线写过的会话都会产生 v3 generation，0.1.3 线读不了**（note:170）⇒ 回滚只等于"回到迁移前的日志快照"，对已用新线继续工作的会话不能无损回退。

**四项前置（负责人已采纳"四前置照办"）**：① 理由摆正；② 独立 `DSH_HOME` 整份副本验证；③ **先证实迁移源谱系**（远端是个人 fork，`master 47f9438` 是否确为上游支持线需先证明）；④ 出具"**迁移后免费 / 仍需自建**"清单（分析师条件）。**且不与动作 MVP 捆绑**（产品经理条件）。
