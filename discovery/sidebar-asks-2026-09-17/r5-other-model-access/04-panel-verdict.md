## 二、架构视角对 R4 理由的更正（本议题最有价值的一条）

原文理由「日志合规地记录一次**并未真正执行**的调用」**不准确**——调用确实执行了。**假的是日志对这次执行的描述**，且**可指名**：

- `packages/core/agent-loop/src/agent.ts:542-547` 造 header（含 `config`／`system`／`tools`），`:552`／`:555`／`:561` 写进日志；
- CLI 侧 README `:176` 说 `model` 省略时由 project/user settings 选择，`:181` 说 `agentOptions`／输出 schema／工具过滤被共享服务拒绝 ⇒ 日志里 `request/header` 的 model 字段是**本进程无法证实的声明**；
- **最要命的是**：`packages/core/agent-loop/src/invariant.ts:31-38`、`:39-42`、`:44-52` **全是日志内部自洽性检查**，证明不了「执行与日志相符」，因此对这类**描述失真结构性失明**。理由必须换成这一条，否则将来会有人以为「不变量会拦住它」。

**主 agent 复核：成立。** 逐字读到 `:39-42` 的 `const expected = session.deriveMessages()`（比对出站请求与日志推导，失败信息自称 `log-reconstruction desync`）与 `:44-52` 的 `headerMatches`（比对 `options.*` 与折叠出的 header）；并确认 `agent.ts:542-547` 的 header 由 `canonicalHeader({ config, …adapterDefaults, system, tools })` 构造。

**补充的精度**：专家团说两张协议表「各自为政、关系无人声明」，**今天的取值其实一致**（`provider.ts:46-51` 与 `discovery.ts:39-43` 都是那三种）⇒ 问题不是值不同，而是**没有声明派生关系**，将来一方增删即漂移。另：「model-visible ⟺ logged」的权威行是 `packages/llm/llm/README.md:108`，`:12` 是同一页的长摘要行。

## 三、各视角立场

### 产品视角（有保留）

1. **有保留**：R2／R3／R5 照做；R4 同意「现在不做」，但**反对把理由写成永久性技术否定**——两条路线被反复独立实现，需求真实存在，正确形态是「**边界未定，暂不做**」。
2. **最该砍**：R1 的「无条件删除默认值」按现措辞——若不先确定「未声明协议」在设置页**长什么样**，删默认只是把失败率从系统转嫁给用户。
3. **必答**：谁定 `api` 的 UI 归属与默认呈现（每 route 还是每模型；`catalog.ts:878` 三处可写，UI 不知谁是权威）。
4. **会误解的事**：`discovery.ts:300-305` 的错误文案把「我们要你选协议」包装成「输入模型名」。
5. **翻转条件**：若出现做到「完整工具循环 + 无状态」且 transcript 有**稳定契约**的实现，翻转支持 R4。

### 架构视角（有保留）

1. **有保留**：R3 不应独立存在；R4 的理由必须重写。
2. **最该砍**：把 R3 从独立一条降为 R1 的附庸——R1 决定**顺序**，R3 只决定**措辞**。
3. **必答**：`api` 的权威归属必须是**包内 owner**（`PROTOCOLS` 与 `LISTABLE_PROTOCOLS` 之间选一个真相来源），不是 UI owner。
4. **会误解的事**：`attribution.ts:61` 的「omission cannot suppress attribution」——契约只管 HTTP 且无门禁，非 HTTP provider **天然在覆盖之外**，用户会以为「凡是出网都带身份」。
5. **翻转条件**：若 `invariant.ts` 增加「**执行保真**」维度（要求外部执行通道也产出可核验的等价事件），从「不做」改为「可以做，但必须先有这个门」。

### 业务分析视角（反对）

1. **反对——只反对 R6 的断言形式，不反对其动作**：「0 个方向需要改会话格式」把**范围判断**写成了**事实判断**；支撑它的四条只覆盖「模型调用」这一种执行体，审计上不能用未验证的全面判断关闭范围问题。
2. **最该砍**：R6 的「0 个方向需要」半句，改成「本议题范围内未发现」，举证责任留在记录里。
3. **必答**：谁签字确认风险清单与该注释的一致性——`discovery.ts:293-298` 已书面承认因果链而风险清单未收录，否则这是一个**无主的已知缺陷**。
4. **会误解的事**：风险条目 `../05-risks-and-gates.md:33` 的对策措辞含「**降级**」，读起来像完成态；但仓库里**没有任何降级机制**（`discovery.ts:300-305` 是拒绝 + 手工录入，`catalog.ts:878-882` 是报错）⇒ 风险条目被读成已实现能力，是审计上最危险的一类信号。
5. **翻转条件**：若外部那条「把只在一种协议上可用的模型留在同一张能力表、靠文档告知」被证实为同类问题的上游先例，下调 R1 紧急度但不翻转（风险条目自身写了「不得让列表里可选、调用必然失败成为常态」）。

## 五、三视角一致同意

1. **R1 是既有约定的执行，不是偏好**：不得在实现里藏默认值 + 配置错误须响亮失败 + 姊妹路径早已如此 ⇒ **让发现路径采纳调用路径已有的纪律**，这是本议题最强内部论证。
2. **R2 指向一处正在发生的错误归因**，且仓库已在注释里书面承认该因果——**已知、未修、未入风险清单**。
3. **R3 是复制而非新造**。
4. **R4 的仓库内理由成立**，但须按第二节的修正表述；**外部半句降级为「未发现先例」**。
5. **R5 有仓库内部支撑**：风险条目自身的对策就是「按模型声明选择 API」，即声明优先于探测/重试。
6. **外部证据整体不足以承重**（14 个来源主体、主 agent 未自核、仅 1 条双源、含 1 条已撤回预设）⇒ **不得写入门禁条款**，只能标方向性。
7. 本议题仅只读取证，未改任何文件。

## 七、程序建议（照录）

**拆成两个独立议题，且不是「整体关闭只留协议错配」**：甲「协议错配」（R1–R3）立刻做，全部落在 `packages/llm/llm-pi-ai` 加一处 UI 透传面；乙「CLI 路由」（R4／R5／R6）作为**决定记录**单独归档、**必须保留而非关闭**——R4 是防止将来有人把 CLI 塞成 LLM adapter 的**唯一护栏**，一旦无记录，README 的「final text only」与「一切可从会话日志重建」会被误读为彼此兼容。
